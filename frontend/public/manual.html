一产品简介

解决什么问题：安全设备（天眼 / HIDS / WAF 等）每天产生海量告警，人看不过来（告警疲劳）。本平台把「规则秒拦 + 白名单降噪 + 便宜模型初筛 + 贵模型深度研判」编排成流水线，把上千条告警压到每天真正需要人看的少数案件。

价值说明
降噪用固有免疫秒拦 + 免疫耐受白名单 + 便宜初筛模型（杏仁核），把海量告警压到可处理量级，贵的深度模型只醒「真正可疑的那几条」
越用越准分析师判定回写白名单/黑名单；夜间巩固把当天案件蒸馏成检索记忆，供后续研判参考
风险档位管理层拨「风险旋钮」，全局换挡（宽松 / 正常 / 保守 / 战时）

双术语体系：界面支持「生物术语 / 安全术语」一键切换（如「丘脑」↔「原始告警」、「免疫」↔「规则库」）。本手册用生物术语并括号标注安全含义。

cd backend && python3 -m uvicorn app:app --port 8000     # 后端
cd frontend && npm install && npm run dev          # 前端（另开终端）

  • nginx 托管前端静态 + 反代 /api（默认 80 端口，HTTPS 见 nginx.conf）。

一条告警的完整旅程

① 免疫耐受（白名单） → 命中「已知好」签名，降级（留痕，不丢弃）
② 固有免疫（黑名单） → 命中「已知坏」签名，置信度 0.95 秒拦，不调模型
③ 杏仁核（快模型）   → 逐条打分，低于抑制线 → 降级
④ 黑板（相关性加权） → 弱信号拼链，计算案件强度
⑤ 实体图（连通分量） → 关联同一实体的告警聚成「案件」
⑥ 前额叶（系统2）    → 案件顶出后深度研判，出结构化报告
⑦ 分析师判定        → 误报写白名单 / 真阳写黑名单
⑧ 夜间巩固          → 当天案件蒸馏成检索记忆（供系统2 RAG）
设计原则：抑制 = 降级 + 留痕，永不静默丢弃。每条被压掉的告警都能在「丘脑」页看到原因，必要时一键「放回」。

关键概念详解

签名 Signature：把一条告警的「形状」抽成稳定模板——掩码掉会变的 token（IP/哈希/独立数字/UUID），保留语义 token（主机名/账号/描述词）。svc_backup 登录跳板机 和 svc_backup 登录数据库 是不同签名；资产A 的端口扫描 和 资产B 的端口扫描 也是不同签名（asset 不掩码）。

案件强度：max(各告警置信度) + min(链路加成上限, 链路加成 × (告警数-1))。告警越多、置信度越高，案件强度越高（用于展示排序）。

风险分 Risk：资产价值 × 攻击得逞 × 危害，三维度归一化到 0-1。资产价值来自「内部资产清单」匹配（普通 0.3 / 重要 0.6 / 核心 1.0，未匹配默认 0.3）；攻击得逞（阻断/失败 0 / 成功 0.7 / 失陷 1.0，缺失保守取 1.0）；危害（低 0.25 / 中 0.5 / 高 0.75 / 危急 1.0，缺失取 0.5）。缺失维度标记 risk_incomplete。

顶出 Escalate：案件风险分 ≥ 风险阈值（默认 0.3）→ 唤醒系统2 深度研判。风险分替代旧版置信度排序决定顶出优先级。

五数据接入

平台支持多通道 + 多来源接入，三条通道汇聚到同一条处理流水线。

通道入口鉴权用途

syslog 接收

监听 UDP/TCP :5514，解析 RFC3164 / RFC5424 标准 syslog。默认只绑 127.0.0.1；要收远程设备日志，把监听地址设为 0.0.0.0 并放行端口（Docker 需在 compose 取消 5514 端口映射注释）。

HTTP JSON API

单条信号（signal）字段：

字段说明必填
time事件时间是
source来源标签（调用方自报，如「天眼」）是
asset资产/主体（主机名/账号）是
type告警类型是
raw原始描述是
curl -X POST http://127.0.0.1:8000/api/ingest \
  -H "X-API-Token: <token>" -H "Content-Type: application/json" \
  -d '{"signals":[{"time":"2026-08-28 10:00:00","source":"天眼","asset":"web-01","type":"ssrf","raw":"探测云元数据 169.254.169.254"}]}'
未配置 token 时 /api/ingest 拒绝接入（fail-closed）。

来源识别（syslog 专属）

syslog 进来后按「来源映射」自动识别来源，判定优先级：

ip（来源地址）> tag（应用名）> hostname（主机名）> facility（RFC 编码）
  • 均为大小写不敏感的子串匹配；ip 可为完整地址或网段前缀（如 10.20.）。
  • 映射在「高级设置 → 数据接入（syslog）→ 来源映射」编辑，四组键值 ip / tag / hostname / facility。
  • 设备需发标准 RFC3164/5424 syslog；非标准格式会被丢弃。
  • 未命中任何映射 → 落到 facility 内置默认（认证/系统/审计/其他），不显示在「已配置来源」，但会在丘脑看到。
  • 有中转 rsyslog 时，ip 判定用的是中转机 IP，不是原始设备 IP。

来源解析（精确实体）

  1. 填来源名（如「天眼」）+ 贴样本日志（2~5 条，每行一条）。
  2. 点「生成解析配置」→ 系统用模型生成规则，显示可编辑预览。
  3. 确认后「保存解析配置」。
  4. 之后该来源的日志按规则确定性解析、精确实体拼链；可点规则条目查看/编辑/启停/删除完整 JSON。

Filebeat 文件日志采集（Kafka 中转）

安全设备把日志写到本机文件，Filebeat 尾部采集 → Kafka → 后端消费，与其它通道走同一条流水线。

  • 文件命名约定：<类型>-YYYY-MM-DD-HH.log（如 ips-2026-09-20-18.log、webids-…、waf-…、hids-…）。
  • 来源识别靠 Filebeat 的 fields.source（tianyan / waf / hids）映射到「天眼 / WAF / HIDS」，再走对应解析规则。
  • 日志目录挂载：docker-compose.yml 里 TIANYAN_LOG_DIR / WAF_LOG_DIR / HIDS_LOG_DIR，改路径在 .env 设这三个变量。
  • Kafka 连接：NEUROIMMUNE_KAFKA_BOOTSTRAP_SERVERS（默认 kafka:9092）、NEUROIMMUNE_KAFKA_TOPIC（默认 neuroimmune-logs）。

风险模型（风险分）

案件是否顶出由「风险分」决定（替代旧版按置信度排序）。风险分 = 资产价值 × 攻击得逞 × 危害：

字段说明默认
risk_threshold案件风险分 ≥ 此值才考虑顶出0.30

九常见问题 FAQ

Q1：为什么「已配置来源」显示「暂无数据」？

库里还没有该来源的告警；或设备数据没匹配上来源映射。去「丘脑」看实际进来的 source 是什么，回来改映射。

Q2：标记误报后，未来同样的攻击会不会被漏掉？

系统按「签名/形状」匹配白名单，无法区分「同形状的运维操作」和「复刻它的攻击」。但有三层兜底：① 降级留痕（丘脑可见、可放回）；② 白名单 TTL 到期自动失效（默认 90 天）；③ 签名细粒度（区分资产/账号/主机名）。

Q3：「证据不足」和「关闭」有什么区别？

「证据不足」把案件置为「挂起 On Hold」，仍算待处理；「关闭」是终态，但可「重启」重新打开。

Q4：状态为什么是英文？结论为什么是中文？

状态字段（New/In Progress/On Hold/Resolved/Closed）保持英文；结论（真阳性/可疑/误报/良性/证据不足）显示中文。

Q5：如何让平台接收远程安全设备的日志？

①「高级设置 → 数据接入」把 syslog 地址设为 0.0.0.0（Docker 需映射 5514 端口）；② 防火墙放行 5514；③ 设备端配置 syslog 转发到 平台IP:5514；④ 在「来源映射」配好设备 IP/TAG/主机名 → 标签。

Q6：清空数据库会清掉记忆吗？

不会。「清空数据库」只清告警/案件/报告等，记忆在「高级设置 → 记忆管理」单独清。

Q7：批量标记误报为什么有的案件选不了？

已标记（有结论）的案件不可再被批量选中，避免重复标记。如需重新处理，进案件详情单独改结论。

Q8：模型配好了，但后端一直报「模型连接失败 / Kafka 信号处理失败」？

用「高级设置 → 模型接入」页的「测试」按钮直接测，看是 DNS / 连接 / 鉴权哪一类；或 docker compose exec backend python3 -c "import socket; print(socket.gethostbyname('域名'))"。

报错原因解法
Name or service not known容器解析不了模型域名（内网域名最常见）给 backend 加 extra_hosts 映射到真实 IP，或 base URL 直接填 IP
Connection refused / timeout域名能解析但连不上查防火墙、端口放行、容器与模型的网络
401 / 4xxAPI key 填错回模型接入页把 key 重新填对

extra_hosts 写法（docker-compose.yml 的 backend: 段下）：

    extra_hosts:
      - "higress.app.stg:<实际IP>"

然后 docker compose up -d --no-build backend。

Q9：Filebeat 起来了，但一条日志都采不到？

  • 原因：日志目录/文件对 Filebeat（容器内 uid=1000）不可读。
  • 排查：docker compose logs filebeat 看是否 permission denied；或用 docker run --rm -u 1000:1000 -v <日志目录>:/logs:ro alpine sh -c 'head -1 /logs/*.log' 模拟读。
  • 解法：sudo chmod -R a+rX <日志目录>（目录 r-x、文件 r，且整条父目录链每层都要 x 能进）。
  • ⚠️ 别用 user: root：Filebeat 以 root 跑会报 config file must be owned by the user running Filebeat（挂载进来的 filebeat.yml 属主是 uid 1000），反而起不来。

Q10：两个模型（系统1 + 系统2）是两个不同的 key，怎么配？

系统1 用 NEUROIMMUNE_API_KEY，系统2 用 NEUROIMMUNE_DEEP_API_KEY。.env.example 里省略了系统2 的 key（靠回退到系统1），所以两个不同 key 时必须显式加 NEUROIMMUNE_DEEP_API_KEY；或在前端「模型接入」页的「前额叶（系统2）」段单独填 API key。

Q11：设备日志偶尔丢最后几行 / 采不全？

设备若用 rename 式 logrotate（改名 .log → .log-YYYYMMDD），Filebeat 只尾随 *.log，改名后设备若还在写旧文件，最后几行会时有时无地丢（竞态）。建议 logrotate 改用 copytruncate（原地截断、路径不变），或保证设备在轮转前就切到新文件。
